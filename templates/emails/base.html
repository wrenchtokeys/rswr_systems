{% comment %} The one chassis every RS Systems email renders through — the Django notification templates by extending it, and send_branded_email() by rendering emails/generic.html, which extends it too. There is no second shell; before this there were two, and they shared no header, button, type scale or colour. DESIGN TOKENS ARE HARDCODED HERE ON PURPOSE, with one exception. `branding` carries the shop's identity (name, address, contact, logo) and `branding.primary_color`, which is the shop's Tenant.brand_color when it has set one. Everything else in the palette — the ground, the ink ramp, the hairline, the radii, the type scale — is fixed, because the EmailBrandingConfig singleton's colour and font fields are platform-wide and letting them through is how the platform owner's look leaked onto other shops' mail. Do not reintroduce branding.background_color, branding.body_font or branding.button_border_radius here. PLATFORM vs SHOP. Nothing in this file special-cases it. An email from RS Systems itself (subscription, billing, account) goes out through send_branded_email(platform=True), which builds `branding` with no tenant — so company_name is "RS Systems", primary_color is platform blue, and `header_meta` carries the shop's name on the right instead. A shop's brand colour must never appear on a platform email. Context contract: branding required dict — EmailBrandingConfig.get_tenant_context() header_meta optional str — right side of the header (job ref, shop name) base_url absolute site root, injected by NotificationTemplate.render Blocks: email_title, preheader, content, unsubscribe_url See docs/operations/SES_OPERATIONS.md before changing email content. {% endcomment %} {% block email_title %}{{ branding.company_name }}{% endblock %} {% comment %} Inbox preview line. Without one, clients scrape the top of the body and show the shop name a second time next to the subject. The zero-width padding after it stops Gmail pulling the first line of the headline in. {% endcomment %}
